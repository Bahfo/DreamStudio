# Contributing to DreamStudio

Welcome DreamStudio Developers! In this section, we explain to you exactly contribution criteria and
terms and conditions to get you started contributing to DreamStudio.

## Contribution Hierarchy
DreamStudio repository follows a strict hierarchy of priority while contributing, not all people are
allowed to contribute directly into the main branch, and it must be that to disallow unrecognized 
contributions or crashing codes.

Firstly, the main contributor of this project is Bahaa Nofal. He is the owner of the repository and 
has the permissions to change any section in the repository and/or permit/prevent any changes to be 
made. 

Secondly, under the main contributor comes vice contributors, which handle pull requests and manages
the contribution. This section also comes with different hierarchies. So there are vice contributors, 
and vice contributors to those vice contributors (called Elders). 

Lastly, a contributor, who comes after an elder. Contributors are assigned with tasks that are requested
on the main forum.

## Rules of Contribution
There are some rules that should be followed while contributing to the repository (alongside the code
quality discussed in *Code Quality Assurance Rules*). These rules define how a person can contribute
to any opened task or request a new task and contribute to it.

1. **Code Quality Assurance** Rules must be obayed and followed exactly as listed.
2. Contributions on opened tasks are allowed to be recieved only on the main forum and not on main repository.
3. Every single patch sent must contain a Developer's Certificate of
Origin (DCO) where you sign your real name and email at the end of the patch (*Example*: `Signed-off-by: Real Name <email@example.com>`).
4. Each patch must make exactly one logical and independent change. Do not bundle a bug fix, a style cleanup, and a new feature together. Instead, bundle each in a separate patch. If they are unrelated, they must be split into an ordered patch series.
5. Every single patch within a multi-patch series must compile and run
successfully. You cannot send a broken code and expect us to solve or fix it. Either send it clean or expect it to be trashed.

#### Submission Rules: 
DreamStudio uses mailing instead of Pull Requests to handle submission. Please follow the following rules while submitting:
1. **NO HTML EMAILS**: Your mail must be sent in absolute plain text. HTML formatting or rich text will be automatically dropped (even if it has the cleanest and safest code ever).
2. Contributors must ensure that mails are sent through the main forum and not via gitlab, github, or any other platform (Do not worry about listing your name in contributions, we handle that separately by assigning your real name to the contributors thanking list inside the repository, and giving you a mention in the main forum).
3. While contributing in the main forum, please make sure to look up 
the `MAINTAINERS` file in the root directory to find out exactly who is the maintainer for your specified patch, as sending a patch to the wrong maintainer is not recommended.

Contribution hierarchy is increased only with trust and active contribution, and penalties may get you out of contribution, so please be careful while contributing.

## Contributing with Documentation Only
Documentation rules are a bit different. We do not force you to follow a strict style while documenting, but we expect you to do the following:
1. Please make sure your documentation is understandable by having a formal language, and a meaningful explanation.
2. Do not turnacate meaning or purpose of the documented method unless it is required to do so.

Documentation requests are handled inside `Documentations Contributing` in the root directory inside the forum. 

## LLM Contributions
For LLMs, or people that wants to use LLM while contributing. Please follow the strict rules of LLMs contributions listed inside /.ai and /.agents folders.
